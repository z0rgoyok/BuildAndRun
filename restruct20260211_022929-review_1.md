# Final Gate Review: Presentation Services и границы Clean Architecture

- Ветка: `restruct`
- Дата/время: `2026-02-11 02:29:29`
- Область ревью: все места, где presentation-слой берет на себя orchestration уровня application/domain или напрямую работает с application ports.
- Цель: найти системные нарушения границ слоев, не внося изменений в код.

## Ключевой вывод

Архитектурная граница `Presentation -> Application -> Domain` соблюдается непоследовательно. Для части фич presentation-сервисы работают как application orchestrators и напрямую используют application ports, а не use cases. Это уже не локальный случай `AppKanbanService`, а повторяющийся паттерн в нескольких контекстах.

## Findings (по убыванию критичности)

### 1. [CRITICAL] Существенная часть бизнес-orchestration находится в presentation-сервисах, минуя application use cases

1) Что проблемно

- `AppGitActionsService` напрямую оркестрирует git-сценарии (push/pull/create PR/complete/remove/prune): `presentation/context/gitactions/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/gitactions/impl/AppGitActionsService.kt:3`, `presentation/context/gitactions/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/gitactions/impl/AppGitActionsService.kt:47`, `presentation/context/gitactions/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/gitactions/impl/AppGitActionsService.kt:240`.
- `AppWorktreesService` напрямую работает с `GitClient` и `PreferencesStore` помимо use case: `presentation/context/worktrees/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/worktrees/impl/AppWorktreesService.kt:6`, `presentation/context/worktrees/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/worktrees/impl/AppWorktreesService.kt:71`, `presentation/context/worktrees/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/worktrees/impl/AppWorktreesService.kt:176`.
- `AppEditorsService`, `AppSettingsService`, `AppGroupsService`, `AppSidebarService` также напрямую работают с `PreferencesStore`/port-ами: `presentation/context/editors/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/editors/impl/AppEditorsService.kt:3`, `presentation/context/settings/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/settings/impl/AppSettingsService.kt:3`, `presentation/context/groups/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/groups/impl/AppGroupsService.kt:3`, `presentation/context/sidebar/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/sidebar/impl/AppSidebarService.kt:3`.

2) Почему это риск

- Бизнес-поведение размазывается по UI-слою; сценарии труднее переиспользовать и тестировать вне UI wiring.
- Появляется несколько “точек истины” для правил, растет риск регрессий при изменении поведения.
- Нарушается заявленная архитектурная цепочка из README (`Presentation -> Application -> Domain`): `README.md:27`.

3) Как улучшить

- Вынести сценарии в application use cases для git-actions/kanban/sidebar/editor-preferences/settings-preferences.
- Оставить в presentation только: сбор input, вызов use case, маппинг результата в state.

### 2. [CRITICAL] Presentation core (`AppBootstrapper`, `AppStateRefresher`) содержит application-level orchestration и persistence coordination

1) Что проблемно

- `AppBootstrapper` загружает persisted данные и заполняет state напрямую через `PreferencesStore`: `presentation/common/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/core/AppBootstrapper.kt:3`, `presentation/common/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/core/AppBootstrapper.kt:36`, `presentation/common/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/core/AppBootstrapper.kt:52`.
- `AppStateRefresher` одновременно “публикует UI state” и выполняет persistence/cleanup: `presentation/common/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/core/AppStateRefresher.kt:20`, `presentation/common/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/core/AppStateRefresher.kt:68`, `presentation/common/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/core/AppStateRefresher.kt:93`.

2) Почему это риск

- Класс UI-синхронизации становится узлом бизнес-сайд-эффектов и хранения.
- Изменения в хранении или правилах выбора/очистки данных затрагивают presentation core.

3) Как улучшить

- Разделить responsibilities:
- `StatePublisher` (только publish/select UI projection).
- `SessionRestoreUseCase`/`PersistSelectionUseCase`/`PersistKanbanTasksUseCase`/`CleanupRepositoryDataUseCase` в application.

### 3. [HIGH] Скрытые transitive-зависимости на application-слой в context-модулях presentation

1) Что проблемно

- Модули `editors`, `gitactions`, `sidebar` не объявляют прямую зависимость на `application:*`, но используют application-типы в коде.
- Пример: `AppEditorsService` импортирует `PreferencesStore`/`EditorOpening`/`SystemOpening`: `presentation/context/editors/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/editors/impl/AppEditorsService.kt:3`.
- При этом `presentation/context/editors/build.gradle.kts` не содержит `projects.application.*`: `presentation/context/editors/build.gradle.kts:13`.
- Аналогично для `gitactions` и `sidebar`: `presentation/context/gitactions/build.gradle.kts:13`, `presentation/context/sidebar/build.gradle.kts:13`.
- Причина: `presentation.common` транзитивно тянет application-модули: `presentation/common/build.gradle.kts:13`.

2) Почему это риск

- Реальные архитектурные зависимости маскируются.
- Любой context-модуль может начать использовать application API “случайно”, не фиксируя это в своем build-файле.

3) Как улучшить

- Сделать зависимости явными и временно зафиксировать текущую связанность.
- Затем сократить связанность, вынеся orchestration в use cases и убрав лишние application imports из presentation context-модулей.

### 4. [HIGH] Правила валидации и формирование domain failures частично живут в presentation

1) Что проблемно

- `AppGroupsService` строит `DomainFailure.Validation/Conflict/NotFound` в presentation: `presentation/context/groups/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/groups/impl/AppGroupsService.kt:70`, `presentation/context/groups/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/groups/impl/AppGroupsService.kt:82`, `presentation/context/groups/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/groups/impl/AppGroupsService.kt:94`.
- `AppKanbanService` валидирует заголовок и устанавливает `DomainFailureCode` в presentation: `presentation/context/kanban/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/kanban/impl/AppKanbanService.kt:117`, `presentation/context/kanban/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/kanban/impl/AppKanbanService.kt:122`.

2) Почему это риск

- Правила становятся зависимыми от UI entrypoint.
- При добавлении второго входа (другой UI/CLI/API) поведение может разойтись.

3) Как улучшить

- Перенести валидацию и формирование `DomainFailure` в application use cases.
- В presentation оставить только отображение результата.

### 5. [HIGH] Нарушение правил локализации и stringly-typed sentinel в `AppGitActionsService`

1) Что проблемно

- Захардкоженные пользовательские строки в success state: `presentation/context/gitactions/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/gitactions/impl/AppGitActionsService.kt:55`, `presentation/context/gitactions/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/gitactions/impl/AppGitActionsService.kt:72`, `presentation/context/gitactions/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/gitactions/impl/AppGitActionsService.kt:109`.
- String sentinel `"detached HEAD"`: `presentation/context/gitactions/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/gitactions/impl/AppGitActionsService.kt:192`, `presentation/context/gitactions/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/context/gitactions/impl/AppGitActionsService.kt:259`.

2) Почему это риск

- Нарушение AGENTS.md: локализация должна быть в shared KMP strings; запрещены stringly-typed enum-like значения.
- Легко получить расхождение поведения из-за опечаток/вариантов формата строки.

3) Как улучшить

- Перенести все UI-success сообщения в `presentation/resources`.
- Заменить string sentinel на доменный тип/признак (`sealed`/enum/explicit flag в модели статуса ветки).

### 6. [MEDIUM] Межконтекстная связанность внутри presentation через `WorktreesOperations`

1) Что проблемно

- `gitactions` зависит от `presentation.context.worktrees` модуля: `presentation/context/gitactions/build.gradle.kts:17`.
- `AppGitActionsService` вызывает операции через `WorktreesOperations`, который реализуется `AppWorktreesService`: `presentation/root/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/AppRootKoin.kt:104`, `presentation/root/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/AppRootKoin.kt:147`.

2) Почему это риск

- Возникает tight coupling presentation-context к presentation-context.
- Бизнес-последовательность “git action -> refresh worktrees” не выражена application-контрактом.

3) Как улучшить

- Вынести “refresh after git mutation” в application сценарий/фасад.
- Привязать `gitactions` к application API, а не к другому presentation service.

### 7. [MEDIUM] Недостаточное покрытие тестами для наиболее рискованных presentation orchestrators

1) Что проблемно

- В presentation-слое есть только тесты для sidebar и update kanban:
- `bridge/src/commonTest/kotlin/app/tich/buildandrun/presentation/app/AppRootSidebarExpansionTest.kt:23`
- `bridge/src/commonTest/kotlin/app/tich/buildandrun/presentation/app/AppRootKanbanTaskUpdateTest.kt:21`
- Нет отдельных тестовых сценариев для `AppGitActionsService`, `AppWorktreesService`, `AppEditorsService`, `AppSettingsService`, `AppGroupsService`, `AppBootstrapper`, `AppStateRefresher`.

2) Почему это риск

- Самые сложные пути (сетевые/git side effects, последовательность операций, ошибки persistence) не зафиксированы тестами.

3) Как улучшить

- Добавить integration-like тесты AppRoot для критичных сценариев:
- push/pull/createPR/complete/remove/prune
- create worktree + copy files + persist base branch
- group CRUD + consistency между group/repository persistence
- bootstrap restore + invalid persisted references cleanup

## Проверка соответствия AGENTS.md

- `DDD/Clean Architecture, strict layer separation`: не выполнено полностью (см. Findings 1, 2, 3, 4, 6).
- `Localization only in shared KMP string files`: нарушено в `AppGitActionsService` (Findings 5).
- `Do not use stringly-typed keys/enums`: нарушено через sentinel `"detached HEAD"` (Findings 5).
- `Max file length <= 350`: соблюдено для просмотренных файлов (крупнейший `AppGitActionsService` = 320 строк).
- `One top-level class per file`: соблюдено в проверенном scope.
- `Fail-fast principle`: соблюдается непоследовательно; в ряде путей ошибки обрабатываются мягко/локально и логика размазана между UI и persistence.

### Допустимое осознанное отклонение

- Composition root в `presentation/root` зависит от разных слоев (`AppRootKoin`): `presentation/root/src/commonMain/kotlin/app/tich/buildandrun/presentation/app/AppRootKoin.kt:30`.
- Это приемлемо как outermost wiring слой, если бизнес-логика не протекает туда. В текущем коде проблема не в самом DI-компоновщике, а в том, что business orchestration находится в presentation services.
